M.O.M.M.A BOT PROJECT WORKFLOW AND INTERVIEW TEST DOCUMENTATION
=================================================

Document purpose

This document records the workflow used to test MOMMA (My Online Mentor
and Model Architect), focusing on how a user creates a project, supplies
project context, and participates in MOMMA’s context-driven interview.
It also records observations from the Hospital Management System (HMS)
test scenario.

1. OVERVIEW: WHAT MOMMA DOES

MOMMA is intended to help a user turn an initial project idea and
supporting materials into a structured, project-specific bot
specification. Rather than immediately generating a generic bot, MOMMA
first gathers context, identifies information that appears to be
missing, asks follow-up questions, and uses the answers to build a more
complete understanding of the project.

The intended high-level workflow is:

Create Project -> Supply Project Context -> Analyze the Context ->
Identify Missing or Unclear Information -> Present Clarifications /
Project Summary -> Conduct an Interview -> Incorporate Answers into the
Project Context -> Prepare the Bot’s Specification -> Generate or
prepare the customized bot output -> Review, test, and refine the result

This document describes the workflow at the user-interaction level. It
does not claim that every future feature or integration is already
implemented.

2. STEP 1 — THE USER CREATES A PROJECT

The user starts by creating a new project in MOMMA and giving it a name
or identifying purpose.

For the test documented here, the project was a Hospital Management
System (HMS).

The project name gives MOMMA a working identity for the conversation and
helps keep the project’s context, answers, and resulting specification
associated with the same project.

3. STEP 2 — THE USER SUPPLIES PROJECT CONTEXT

The user provides an initial description of the project. Depending on
the workflow supported by the application, context may be supplied as
written text and/or supporting files.

For the HMS test, the submitted context explained:

-   The purpose of a Hospital Management System.
-   The operational problems it aims to solve.
-   The main modules, including patient registration, OPD/IPD,
    electronic health records, pharmacy, laboratory, billing, and access
    control.
-   The people who may use the system, including patients,
    receptionists, doctors, nurses, pharmacists, laboratory technicians,
    and administrators.
-   The need for privacy, security, reliability, and coordinated
    workflows.

This initial context acts as MOMMA’s starting point. It is not
necessarily a complete specification. It describes what the user already
knows or has decided and gives MOMMA a basis for asking useful follow-up
questions.

4. STEP 3 — MOMMA ANALYZES THE CONTEXT

After receiving the context, MOMMA reviews it to understand the
project’s purpose, users, requirements, constraints, and likely areas of
uncertainty.

The analysis should distinguish between:

-   Information explicitly provided by the user.
-   Information that can reasonably be summarized from the context.
-   Important details that are missing or ambiguous.
-   Assumptions that still need confirmation.
-   Decisions that have not yet been made.

For example, an HMS description may list many modules but not specify
the target hospital size, the first release’s scope, the expected
operating environment, or how success will be evaluated.

MOMMA should not treat a plausible assumption as a confirmed user
decision. If a detail is important and absent, it should ask the user
rather than silently presenting the detail as finalized.

5. STEP 4 — MOMMA IDENTIFIES INFORMATION GAPS

MOMMA uses its analysis to identify details that may be necessary to
design the customized bot properly.

During the HMS interview test, MOMMA explicitly reported that it could
not find the following information in the supplied context:

-   “How will you know the bot is working well?”
-   “What is the specific target scale (e.g., small clinic vs. large
    multi-specialty hospital)?”

These are examples of context-gap detection. Instead of requiring the
user to rewrite the entire project description, MOMMA asks for the
missing information and allows the user to supply a focused answer.

A useful gap-detection process should avoid asking for information that
has already been clearly supplied, should not repeatedly ask the same
question without a reason, and should keep confirmed details separate
from unresolved ones.

6. STEP 5 — MOMMA ASKS INTERVIEW QUESTIONS

Once the initial context has been reviewed, MOMMA conducts a
conversational interview to fill important gaps and confirm the user’s
intentions.

The interview is adaptive: answers from the user help determine which
questions should come next. The purpose is to understand the project,
not simply to run through an unrelated fixed questionnaire.

A typical interview question may ask about:

-   The project’s intended purpose and target users.
-   The desired role and behavior of the bot.
-   The bot’s tone and communication style.
-   The tasks the bot should help with.
-   Features that are already implemented versus features that are only
    planned.
-   What the bot should do when it cannot answer.
-   Evaluation criteria and success metrics.
-   Target scale, constraints, and technical or regulatory requirements.

In the observed test, MOMMA asked the user to clarify the project’s
scope by asking what type of HMS they intended to build. It offered
examples ranging from a basic academic project to a comprehensive or
production-oriented system, while allowing the user to describe a
different vision.

This approach helps the user make decisions explicitly rather than
having MOMMA decide the scope on the user’s behalf.

7. STEP 6 — MOMMA USES THE ANSWERS TO BUILD A MORE COMPLETE CONTEXT

The user’s answers become additional project context. MOMMA should use
them together with the original description when asking subsequent
questions and preparing the project specification.

For the HMS test, the user supplied detailed answers about the intended
bot and project, including:

A. Bot role and tone - The bot is intended to act as a conversational
assistant and technical co-pilot. - It should help with software
architecture, project planning, backend engineering, system design, and
implementation. - The preferred tone is professional, collaborative,
encouraging, clear, structured, and pragmatic.

B. Intended users and workflows - The described platform includes six
main user-persona groups: doctors and consultants; front-desk staff;
inpatient nurses; billing and accounting staff; pharmacists and
laboratory technicians; and super administrators or hospital
directors. - The described workflows include clinical records,
registration, bed allocation, pharmacy and diagnostics, billing,
administration, and permissions.

C. Fallback behavior - When the bot cannot answer or safely perform a
task, it should acknowledge the limitation, preserve relevant context
where the system supports it, and route the user to an appropriate human
contact or support path. - Clinical safety and access-control boundaries
are especially important in a hospital environment.

D. Implementation status - The user distinguished between architectural
plans and features that are actually built and working. - The supplied
answer described the project as being in a pre-implementation /
architecture-scaffolding phase, with code implementation planned for
later sprints. - Therefore, architectural decisions must not be reported
as proof that the corresponding features have already been implemented
or tested.

E. Target scale - The user supplied a target scale of mid-sized
multi-specialty hospitals with approximately 100–300 beds in India. -
The answer also described a multi-tenant SaaS direction and related
operational requirements.

F. Success metrics - The user supplied four dimensions for evaluating
the technical co-pilot: architectural precision; context continuity and
consistency; actionable, production-ready output; and technical
problem-solving and adaptability.

These answers enrich the project context and help MOMMA produce a more
tailored specification than it could from the initial description alone.

8. STEP 7 — MOMMA SHOULD CONFIRM, NOT INVENT, PROJECT DECISIONS

After several answers, MOMMA may summarize what it believes it has
learned and ask the user to correct any misunderstandings.

This confirmation step is important because a detailed answer can
contain a mixture of confirmed requirements, proposed design choices,
examples, and future plans.

For example, the HMS responses mentioned DPDPA and ABDM compliance,
offline-first PWA functionality, WebRTC telemedicine, payment
integrations, and hospital-specific standards. These should be recorded
as user-provided requirements or proposed architectural specifications,
not automatically treated as implemented capabilities.

MOMMA should clearly distinguish: - Confirmed by the user. - Proposed or
under consideration. - Missing and awaiting clarification. - Planned for
a later development phase. - Implemented and verified through actual
testing.

The project summary should be updated as new answers are received, while
preserving earlier decisions unless the user changes them.

9. STEP 8 — MOMMA PREPARES THE CUSTOMIZED BOT SPECIFICATION

When sufficient information has been collected, MOMMA can organize the
context and interview answers into a coherent specification for the
customized bot.

Depending on the product’s implementation, the resulting specification
may include:

-   The bot’s purpose and responsibilities.
-   Intended users and supported workflows.
-   Tone and response style.
-   Functional requirements and boundaries.
-   Context and continuity requirements.
-   Fallback and escalation behavior.
-   Safety, privacy, and permission constraints.
-   Technical requirements and integrations.
-   Evaluation criteria and test scenarios.
-   A list of unresolved questions or assumptions.

The user should have an opportunity to review and correct the
specification before it is treated as final.

10. STEP 9 — BOT OUTPUT, REVIEW, AND ITERATION

After the specification is reviewed, MOMMA’s intended workflow is to
prepare or generate the customized bot output. Depending on the
implementation, this may include bot instructions, configuration, code,
or other integration-ready artifacts.

The user then reviews the result, tests it against the requirements,
identifies problems, and provides corrections. MOMMA can use those
corrections to refine the specification and the generated output.

The workflow is iterative rather than strictly one-way:

Context -> Analysis -> Interview -> Specification -> Output -> Testing
-> Feedback -> Refinement

The exact generated artifacts and degree of automation depend on the
features implemented in the current version of MOMMA.

11. THE HMS INTERVIEW TEST: OBSERVED BEHAVIOR

Test input: The user submitted a detailed Hospital Management System
description covering the system’s purpose, modules, user personas,
operational challenges, security, privacy, reliability, and concurrency.

Observed behavior: 1. MOMMA began an interview instead of immediately
attempting to produce a complete implementation. 2. It acknowledged that
the supplied context was enough to begin. 3. It summarized its
preliminary understanding of the project. 4. It asked a scope question
about what type of HMS the user intended to build. 5. In the subsequent
interview, MOMMA identified missing details and asked the user to
provide them. 6. The user supplied detailed information about success
metrics, the bot’s role and tone, target users, fallback behavior,
implementation status, and target scale.

What this demonstrates: - The interview can use an initial project
description as its starting point. - MOMMA can ask follow-up questions
about missing project details. - The user can provide focused answers
rather than rewriting the entire context. - The answers can add detail
about behavior, constraints, and project scope.

Observed issue to record: The same question about whether the user
wanted a conversational assistant appeared multiple times in the
supplied interview transcript. This is a useful test finding: MOMMA
should detect when a question has already been answered and avoid
repeating it unless it needs to resolve a genuine contradiction or
confirm a changed requirement.

Another important caution: Some interview answers used confident wording
such as saying that all parameters were “locked in” or that a
production-grade specification was ready. The project record should only
mark a decision as confirmed when the user has actually confirmed it. It
should not imply that planned architecture has been implemented or
verified.

12. HOW TO EVALUATE THIS WORKFLOW

The interview workflow can be evaluated using the following checks:

-   Context understanding: Did MOMMA accurately summarize the supplied
    project?
-   Gap detection: Did it identify important missing information?
-   Question relevance: Were its follow-up questions useful and
    connected to the project?
-   Non-repetition: Did it avoid asking the same question again after
    receiving an answer?
-   Context continuity: Did later questions use earlier answers
    correctly?
-   Assumption handling: Did it ask for confirmation instead of treating
    guesses as facts?
-   Status accuracy: Did it distinguish planned features from
    implemented and tested features?
-   Specification quality: Did the final summary reflect the user’s
    answers without adding unsupported requirements?
-   Correction handling: Could the user correct an inaccurate summary or
    change a decision?

These checks assess the interview and context-building behavior. They do
not, by themselves, prove that the generated bot code is correct,
secure, production-ready, or compliant. Those claims require separate
technical and security testing.

13. SUMMARY

MOMMA’s intended process starts when a user creates a project and
supplies an initial description or supporting context. MOMMA analyzes
that material, identifies gaps and uncertainties, and interviews the
user to obtain the missing information. It combines the original context
with the user’s answers, confirms its understanding, and prepares a
customized bot specification. The intended workflow then proceeds to
bot-output generation, review, testing, and refinement.

The HMS scenario served as a practical test of the early stages of this
process. It showed context-based follow-up questions and the collection
of detailed project requirements. It also revealed areas to monitor,
particularly repeated questions and the need to distinguish confirmed
requirements from assumptions, plans, and implemented functionality.
